# 1日1回、ランダムな「今日のまなざし」通知

日本時間9〜21時の間で、その日の配信時刻をサーバーがランダムに1つ決めます。登録した端末へ、同じ配信タイミングを起点に「30秒、スマホを下ろして街を見てみよう」とWeb Pushを送ります。通知からアプリを開いても、観察タイマーは勝手に開始しません。

時間帯は利用者の希望で9〜21時に設定済みです。個々の端末で別の時刻を選ぶ仕様ではありません。配信時刻より後に登録した端末は翌日から対象になります。登録は端末・ブラウザごとです。

## 現在の状態

アプリとWorkerのコード・SQL・テストを準備済みです。**D1、通知署名鍵、専用レート制限、Cron Triggerの実アカウント設定は別途必要で、実端末への配信は未検証です。** 未設定の間はアプリに「通知サーバーは準備中」と表示し、通知許可を求めません。既存の画像AIや観察機能は通知の設定がなくても利用できます。

## 利用者側の操作

ホームの「今日のまなざしを通知」から「1日1回の通知を受け取る」を押し、ブラウザ・OSの通知を許可します。起動時に勝手に許可ダイアログを出しません。同じ画面で停止や任意のテスト送信ができます。

- iPhone/iPadはiOS/iPadOS 16.4以降が必要です。Safariの共有メニューからホーム画面へ追加し、そのアイコンから開いて許可します。
- AndroidやPCでも、Web Pushに対応したブラウザと通知許可が必要です。完全終了、OSの省電力・集中モード・通信状況によって届かないことがあります。
- テスト通知は利用者が押したときだけ送る追加の1件です。通常の1日1回とは別です。同日の通知は端末上で同じグループにまとめる場合があります。

## Cloudflare管理画面で設定する場合

GitHub連携や有料プランへの変更は不要です。既存の`basho-ai` Workerを使います。

1. 「Storage & databases」→「D1 SQL database」で`basho-notifications`を作成します。Freeを維持します。
2. 作成したD1のConsoleで`migrations/0001_notifications.sql`の3つのCREATE TABLE文を実行します。購読情報・日ごとの時刻・配信済み記録を保存するテーブルです。
3. WorkerのSettings → BindingsでD1を追加します。変数名は`NOTIFICATIONS_DB`、接続先は作成したデータベースです。既存の`AI`と`IMAGE_RATE_LIMITER`を残してください。
4. Rate Limiterバインディングを追加します。名前`PUSH_RATE_LIMITER`、Namespace ID `1003`、Limit `30`、Period `60`秒にします。
5. 公開サイトの`push-setup.html`を開いて「通知用の鍵を作成する」を押します。鍵は管理者のブラウザ内で生成され、サーバー・GitHub・localStorageへ送信・保存されません。作業が終わるまでそのページを閉じないでください。
6. WorkerのVariables and Secretsに公開鍵をTextとして`VAPID_PUBLIC_KEY`へ、秘密鍵をSecretとして`VAPID_PRIVATE_KEY`へ登録します。秘密鍵をチャットやスクリーンショットへ含めないでください。両方とも同じ生成操作で得た組を使用します。`VAPID_SUBJECT`は省略可能で、既定はアプリのHTTPS URLです。
7. Triggers → Cron Triggersに`* * * * *`（1分ごと）を追加します。これは配信時刻を確認する実行間隔で、1分ごとに利用者へ通知する意味ではありません。
8. 最新の`dashboard-worker.js`をコード編集画面の`worker.js`全体へ貼り付け、Deployします。古い284行版には通知処理がありません。
9. アプリを更新し、対象端末で通知を許可して「テスト通知」を押します。サーバーの送信受け付けと端末に実際に表示されることは別なので、実機で確認してください。

`wrangler.jsonc`には、管理画面で作成を確認した`basho-notifications`のDatabase IDを登録済みです。これだけでは実アカウントのWorkerに接続されないため、管理画面では手順3のバインディング追加も行ってください。別アカウントへ移す場合は、`notifications-bindings.example.jsonc`の例に従って実際のIDに置き換えます。例のダミーIDは使わないでください。

## CLIを使う場合

```sh
cd /workspace/design-proto-/ai-service
npx --yes wrangler@4.151.0 login
npx --yes wrangler@4.151.0 d1 create basho-notifications
# 結果の実際のDatabase IDをwrangler.jsoncのd1_databasesに追加してから実行
npx --yes wrangler@4.151.0 d1 migrations apply basho-notifications --remote
```

鍵は、信頼できる手元のPCで`node create-push-keys.mjs /公開フォルダの外の新規ディレクトリ`でも生成できます。既定の出力先は`/tmp/basho-push-keys`です。秘密鍵を静的配信フォルダへ置かないでください。

公開鍵を`wrangler.jsonc`の`vars.VAPID_PUBLIC_KEY`へ追加します。秘密鍵は対話入力で登録し、値をコマンドの引数に書かないでください。

```sh
npx --yes wrangler@4.151.0 secret put VAPID_PRIVATE_KEY
npx --yes wrangler@4.151.0 deploy
```

## 配信と無料枠の範囲

- 通知にAI推論は使用しません。VAPIDと標準Web Pushで送るため、追加の通知配信サービス契約はありません。Workers/D1はそれぞれの無料枠の範囲で使用します。有料プランへ自動変更するコードはありません。
- 1分ごとのCronは1日1440回です。D1の行数・読み書き数、WorkerのCPU/リクエスト数、Pushサービスの制限もあります。無料枠超過や障害時は配信が止まる場合があります。
- 最大500端末の試作用です。1回のCronで最大10端末を処理するため、登録数が多いと何分かに分かれます。21時以降は送信せず、取りこぼしを翌日に再送しません。
- 配信前にD1で端末と日本日付の組を一意に確保します。同じCronの重複実行や再実行で重複送信しません。不明な送信結果も同日に再試行しないため、「必ず1件届く」保証はありません。
- 通知には写真・記録文・利用者名を含めません。保存するのはPush接続先、ランダムな管理トークンのハッシュ、登録時刻、日別配信記録です。生の管理トークンはそのブラウザだけに保存します。
- 通知停止で端末の購読を解除し、サーバーの登録も削除します。通信障害でサーバー削除を確認できない場合は、その旨を表示します。期限切れ接続先はPushサービスの404/410応答で削除し、配信履歴は約14日で整理します。
- ブラウザデータ消去やVAPID鍵の変更では、通知の再登録が必要になる場合があります。鍵を不用意に再生成しないでください。

## 検証

`node --test tests/*.test.mjs`と`python3 tests/notifications.browser.py`で購読の管理、署名、日付・時間帯、重複Cron、通知停止、期限切れ、許可ダイアログのタイミングを検証します。SQLiteを使うサーバーテストとモックのブラウザテストであり、実際のApple/Google/MozillaのPushサービスへの配信を証明するものではありません。
